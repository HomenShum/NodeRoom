The important architecture point:

Agents do not own raw writes. The harness owns lock, CAS, proposals, and trace.

The README’s managed-lock section already states this clearly: the production bundle exposes write_locked_cells / write_locked_cell_results; the runtime acquires the range lock, writes with CAS, drafts if blocked, releases in finally, and returns coordination evidence.

The Algorithm Artifacts section is also important: the model can submit a deterministic calculation artifact, but the artifact returns patch bundles and does not commit; managed writes still own lock/CAS/review/draft/trace.

- tool count

- time

- cost

NodeRoom / NodeAgent End-to-End Design Intent

1. Original premise: build a clean agent harness, not just a chatbot

The earliest design intent was to define a clean AI agent harness architecture. The goal was to separate the model from the environment around the model. The model reasons, but the harness owns tools, memory, state persistence, checkpointing, approval gates, and recovery.

The first clean architecture looked like this:

  skills.md

  config.json

  templates/

    memory.ts

    state.ts

    filesystem/

    terminal/

    search/

  guardrails/

    approval.ts

    circuitBreaker.ts

    sanitize.ts

tests/

package.json

tsconfig.json

The important principle was:

The model is the brain. The harness is the operating system.

The model should not own state, retries, permissions, tool safety, or high-impact actions. Those belong to the harness. This is why durable state, hard execution rules, and approval gates were part of the initial design.

2. Refactor into a signature engine: src/nodeagent

The next design refinement was about identity and maintainability. Instead of scattering agent logic under generic src/core, the agent engine should live under a clear signature namespace:

      adapter.ts

      finance/

      mcp/

      integration/

    guardrails/

      approval.ts

      circuitBreaker.ts

      dataSanitizer.ts

      evaluator.ts

  shared/

    types/

    utils/

  ui/

The reasoning was practical: if NodeAgent is the core intellectual asset, it should be easy to find, explain, and eventually distribute.

The import style should also reflect that:

{

  "compilerOptions": {

    "paths": {

      "@nodeagent/core/*": ["src/nodeagent/core/*"],

      "@nodeagent/models/*": ["src/nodeagent/models/*"],

      "@nodeagent/skills/*": ["src/nodeagent/skills/*"],

      "@nodeagent/guardrails/*": ["src/nodeagent/guardrails/*"]

    }

  }

}

The core idea became:

NodeAgent is the named harness layer inside NodeRoom.

It is not just a pile of tools. It is the reusable orchestration layer.

The intention was:

9. Persistent text streaming: live response plus durable replay

The design then added Convex persistent text streaming.

The goal:

The initiating user sees the agent stream immediately.

Other users or refreshed clients can recover from persisted chunks.

The final message is durable.

The intended flow:

1. User submits a request.

2. Convex mutation creates message/job/stream metadata.

3. Convex HTTP action drives the LLM stream.

4. Owner sees token-level output.

5. Convex stores chunks sentence-ish / block-ish.

6. Other clients observe persisted stream body.

7. Final text is patched into durable message history.

This is not meant to stream every token into spreadsheet cells. It is meant for agent narration, progress, and long-form responses.

The design distinction:

Agent narration:

  persistent text stream

Spreadsheet truth:

  validated patch bundle

Human typing:

  local optimistic edit, then committed value

Agent computation:

  branch / scratchpad, then patch bundle

The core rule became:

Stream progress; commit patches.

This avoids bandwidth blowups and avoids treating every token as a database mutation.

12. Semantic Rebase: CAS plus reasoning

The next major design idea was Semantic Rebase.

Plain CAS says:

I read version 7.

I want to write version 8.

If the current version is still 7, commit.

If not, reject.

Semantic Rebase says:

I read the base state.

The current state changed.

My proposed state is now stale.

Instead of blindly failing or overwriting:

  compare base/current/proposed,

  gather context,

  reason about intent,

  and produce a safe resolution.

The design phrase:

Compare → Reason → Swap.

The world model for semantic rebase includes:

Historical state:

  previous versions, prior reports, immutable facts

Surrounding state:

  neighboring cells, row/column labels, formulas, dependency graph

External truth:

  Linkup search results, source documents, filings, news

Human intent:

  comments, active edit state, review round, task owner

Agent intent:

  original prompt, tool results, patch bundle, evidence

Example:

Base C2 = 12%

Human current C2 = 13% because VP wants a conservative base case

Agent proposed C2 = 14% from a management update

Resolution:

  keep 13% in Base Case

  move 14% to Upside Case

  add note explaining both

  mark needs_review

The important safety rule:

The LLM may propose the resolution, but Convex CAS still commits the final write.

Semantic Rebase is not “let the AI overwrite conflicts.” It is a structured review mechanism for meaningful conflicts.

13. Adaptive model routing through OpenRouter

The design then added adaptive model routing.

The goal:

Keep cost down.

Keep latency down.

Improve workflow completion.

Reserve expensive reasoning models for tasks that truly need them.

The routing matrix:

extract:

  cheap/fast model for structured extraction

speed_reasoning:

  fast low-cost model for summarization and simple chat

deep_reasoning:

  stronger model for semantic rebase, diligence, final reports

coding/math:

  stronger model or deterministic runner for formulas/charts/code

Example workflow routing:

Bulk ingest:

  cheap extraction model

Company research:

  better reasoning model + Linkup

Semantic rebase:

  strongest reasoning model

Runway formula:

  deterministic calculator / code runner when possible

The design principle:

Do not use the most expensive model for every step. Route by task complexity and business risk.

The adaptive router is part of the harness, not the UI. It records model choice, cost, latency, and result quality so the run can be evaluated.

14. Convex vs WebRTC vs OLAP: the systems model

A long part of the design conversation clarified system boundaries.

The final understanding:

Convex:

  live OLTP ledger

  durable transactional truth

  reactive queries

  actions/mutations

  agent job checkpoints

WebRTC / ephemeral relay:

  optional future layer

  cursor/presence/high-frequency draft signals

  not authoritative truth

OLAP:

  future analytics warehouse

  scans across historical jobs, costs, evals, user behavior

  not live editing

The design principle:

Convex is for live operational truth. WebRTC is for optional ephemeral speed. OLAP is for later large-scale analytics.

This matters because character-by-character updates or token-by-token cell writes would blow up the database and network. So the architecture separates:

high-frequency local UI:

  local state / ephemeral signals

persistent text:

  chunked stream records

artifact truth:

  debounced or final patch mutations

agent work:

  branch / scratchpad / patch bundle

analytics:

  export to warehouse later

The important realization:

The bottleneck is not just realtime transport. The bottleneck is per-cell human-agent collaboration without retry storms or bandwidth explosions.

15. Hybrid concurrency model

The design then refined concurrency.

The system should use different mechanisms at different layers:

Local optimistic UI:

  user sees typing instantly

Ephemeral presence / self-intent:

  “Homen is editing C2”

Agent branch / scratchpad:

  agent works without locking the live artifact

CAS:

  final write cannot silently overwrite stale data

Semantic Rebase:

  meaningful conflicts are compared and resolved

Short commit lease:

  only exact targets are protected during final publish

For the canonical problem:

Human editing C2

Agent working on A1:C5

The intended behavior:

1. Human starts editing C2.

2. UI shows local edit immediately.

3. Presence/self-intent marks C2 active.

4. Agent sees A1:C5 overlaps with C2.

5. Agent can continue safe work on non-conflicting cells.

6. Agent does not overwrite C2.

7. Agent’s C2-related output becomes draft/proposal/semantic rebase candidate.

8. Final patch commits through CAS.

The corrected architectural principle:

Do not hard-lock the whole range while the agent thinks. Snapshot, branch, rebase, and commit only clean patches.

This keeps the spreadsheet feeling free while still preserving durable correctness.

Interview answer

If asked, “Why ClickHouse if you already have Convex?” answer:

Convex is the live operating database. It is optimized for small, reactive, transactional state: room messages, cell commits, agent jobs, proposals, and traces. ClickHouse is the analytical warehouse. It is optimized for scanning huge event histories: cost by model, latency by tool, source coverage, no-clobber rates, and eval trends. Putting OLAP scans into Convex would slow the live room; putting live collaboration into ClickHouse would be the wrong database shape.

That is the correct systems answer.

If asked, “Which sponsor tech transfers from AWS-Hackathon?” answer:

ClickHouse transfers directly as the OLAP layer. TrueFoundry transfers as the model gateway pattern. Composio transfers as the downstream action layer. OpenUI transfers as the artifact UI pattern. Langfuse transfers as the LLM trace/eval cockpit. Senso/Cited.md transfers as public citation and context publication. Fal/Cloudinary transfer only if we want rich visual media exports, not as core finance truth. Render transfers as the public demo hosting/deployment pattern.

ClickHouse: exactly how to port it

The AWS-Hackathon repo already has a good ClickHouse pattern: logEvent writes one generation event row with phase, model, provider, draft id, shot id, latency, cost, and success flag. It is intentionally non-blocking and falls back to console logging when ClickHouse env vars are missing, so telemetry never takes down the demo.

It also defines a generations table and a chat_events table. The schema explicitly says chat_events is append-only prompt analytics / Fastino-Pioneer export data, not a transactional app database: no users table, no auth/session table, no mutable product state.

That philosophy is perfect for NodeRoom.

NodeRoom ClickHouse schema

Create a NodeRoom-specific OLAP event set:

CREATE TABLE IF NOT EXISTS noderoom_agent_events (
  ts                DateTime64(3) DEFAULT now64(3),
  event_id          String,
  room_id           String,
  job_id            String,
  run_id            String,
  actor_kind        LowCardinality(String), -- human | agent | system
  actor_id          String,
  workflow          LowCardinality(String), -- startup_diligence | finance_variance | research_enrich
  phase             LowCardinality(String), -- intake | plan | search | write | rebase | eval | export
  model             LowCardinality(String),
  provider          LowCardinality(String),
  tool_name         LowCardinality(String),
  artifact_id       String,
  target_ref        String,                 -- sheet!C2, company_row:acme, memo:block_7
  status            LowCardinality(String), -- ok | failed | needs_review | conflict | skipped
  latency_ms        UInt32,
  input_tokens      UInt32,
  output_tokens     UInt32,
  cost_usd          Float64,
  source_count      UInt16,
  evidence_count    UInt16,
  no_clobber_pass   UInt8,
  privacy_pass      UInt8,
  eval_score        Float64,
  trace_id          String,
  metadata_json     String
)
ENGINE = MergeTree
ORDER BY (ts, room_id, job_id, phase);

Yes — this is the right next abstraction. But I would tighten the language:

Do not call it “zero-latency intelligence.” Call it “speculative intent execution.”
The system is not magically faster; it is spending idle time to prepare likely next work before the user asks for it.

Your control-theory analogy is strong. The product version is:

NodeRoom predicts the next useful diligence step, runs safe read-only or draft-only shadow work, and surfaces ready-to-use suggestion chips. If the user clicks, the result appears instantly; if the user ignores it, the system learns and speculates less next time.

The critical guardrail:

Shadow work may prefetch, draft, summarize, search, and prepare patch bundles. It may not commit durable artifact changes, send emails, create Linear issues, update CRM, or publish anything without the normal harness path.

Your uploaded notes already frame the correct harness split: model reasoning is wrapped by tools, state, memory, approvals, and guardrails, while Convex/persistent streaming and optimistic UI provide the live collaboration substrate.

1. The core idea

In your ball-tracking analogy:

Camera sees ball at t0, t1, t2.
Model processing is delayed.
So the system predicts where the ball will be at t3.
Then it draws the box where the ball should be now.

For NodeRoom:

User asks about CardioNova.
Agent answers company profile.
While the user reads, NodeRoom predicts the likely next questions:
  - competitors
  - pricing
  - hiring signal
  - runway/milestones
  - follow-up email
  - diligence gaps

It runs safe shadow work.
Then the UI shows:
  [Competitors ready]
  [Runway questions ready]
  [Draft follow-up ready]

The user experiences this as “the product knew what I needed next.”

Research is moving in exactly this direction. IdleSpec uses idle time in LLM-agent workflows to generate candidate plans while waiting for observations, then updates its drafting strategy with posterior feedback. Speculative Actions predicts likely future actions with faster models and executes them in parallel to reduce end-to-end latency. PASTE exploits recurring tool-call patterns and data dependencies to run speculative tools while the main agent is still “thinking.”

2. The most important correction

Your draft says:

“If confidence > 98%, the agent doesn’t even wait for a click — it just appends the result automatically.”

I would change that to:

If confidence is high and the operation is safe:
  auto-create a draft artifact or suggestion.

If confidence is high and the operation is irreversible:
  never auto-execute; prepare a one-click approval.

If confidence is high and the operation mutates a shared artifact:
  create a patch bundle or proposal, not a committed write.

This is the same rule browsers use for speculation: prerendering can make navigation feel instant, but it uses memory/network resources and should only be done when likelihood is high; Chrome’s docs explicitly warn not to over-prerender because unused speculation wastes user resources.

So NodeRoom should treat prescience like browser prerendering:

Allowed:
  prefetch
  precompute
  pre-draft
  pre-score
  pre-render

Not allowed:
  pre-send
  pre-commit
  pre-publish
  pre-overwrite

The Speculative Intent Layer predicts likely next user intents, executes only safe shadow workflows, stores results in hidden branch state, and reveals them as suggestion chips, drafts, or one-click actions.

6. Safety tiers

This layer must be tiered. Otherwise it becomes dangerous.

Tier	Shadow action	Example	Auto?
0. Prefetch context	Read-only fetch/search/cache.	Prefetch CardioNova competitors.	Yes, if cheap.
1. Draft artifact	Hidden draft, no shared commit.	Draft runway milestone questions.	Yes, if safe.
2. Suggestion chip	User-visible ready action.	[Show competitors]	Yes.
3. Auto-append to private draft	Adds to private scratchpad, not public artifact.	Private agent prepares follow-up email draft.	Only high confidence.
4. Shared artifact proposal	Creates review proposal, not commit.	Suggest sector classification row update.	Only through proposal.
5. Durable commit	Writes to shared workbook/wiki/task board.	Update company row.	Never purely speculative. Must go through managed CAS/review.
6. External side effect	Gmail, Slack, Linear, Notion, CRM.	Send email / create issue.	Never speculative. One-click approval.

This aligns with the “cost-aware speculative execution” idea: speculation should have an admissibility gate and only run if the operation is side-effect-free, idempotent, or staged behind a commit barrier.

7. How it fits Convex streaming

Do not stream shadow results into the main chat as if the user asked for them.

Use three different channels:

Main agent stream:
  visible response to the user's explicit prompt.

Shadow stream:
  hidden or low-noise progress:
    "Thinking ahead..." only if user opted in.

Suggestion chip:
  visible only when a useful shadow result is ready.

Shared artifact:
  updated only after user click / review / managed CAS commit.

Convex optimistic updates are temporary local UI changes that run when a mutation starts, rerun if local query results change, and roll back/reconcile when the mutation completes. That is perfect for “chip appears immediately” or “queued shadow run” UI, but not a replacement for durable artifact commits.

Convex persistent text streaming is specifically useful for the main agent narration: it streams text over HTTP to the driving client while also storing it in the database so it can be reloaded or viewed by other users; its example notes that HTTP sends tokens immediately while database updates happen at sentence boundaries.

So the rule is:

Explicit agent answer:
  persistent text stream

Speculative result:
  hidden shadow artifact + suggestion chip

Durable spreadsheet/wiki/task change:
  managed patch bundle + CAS/proposal/review

9. The scoring function

Do not run every predicted task. Use a simple expected-value rule.

score =
  confidence
  * estimatedUserValue
  * expectedLatencySavedMs
  * safetyMultiplier
  * freshnessMultiplier
  - estimatedCostUsd * costPenalty
  - riskPenalty

Run a shadow workflow only if:

score > threshold
confidence > minimumConfidence
riskLevel is safe_read or draft
estimatedCostUsd < budget
no private/public violation
no irreversible side effect

A practical threshold table:

confidence >= 0.85:
  run safe read/search prefetch

confidence >= 0.75:
  prepare draft artifact if cheap

confidence >= 0.65:
  show suggestion chip only after cheap metadata prep

confidence < 0.65:
  do not run; maybe only show lightweight suggestion text

risk is proposal/commit/external:
  never auto-run beyond draft/proposal creation

14. Cost control

This is where your design gets serious.

Do not use a big reasoning model to predict every next step.

Use a cascade:

1. Deterministic workflow graph
   startup_profile -> competitors, pricing, runway, open_questions

2. Embedding / keyword classifier
   cheap intent matching

3. Tiny/cheap model
   only if ambiguous

4. Strong model
   never for prediction; only for actual high-risk reasoning

Shadow work should prefer:

- cached source reads
- Linkup standard search, not deep, unless high-value
- deterministic calculators
- existing room context
- draft generation with cheap models

Use deep search / deep model only after click or explicit authorization.

15. What to avoid

This layer can become creepy, expensive, or wrong if not bounded.

Avoid:

- auto-sending emails
- auto-creating external issues
- auto-committing spreadsheet cells
- auto-overwriting human notes
- speculative deep research on every chat turn
- using private context to prepare public chips
- showing too many chips
- keeping stale chips after context changed
- charging expensive model calls for guesses

A good rule:

Speculation can prepare work. It cannot create obligation.

In AI, tabula rasa ("blank slate") and first principles represent two distinct approaches to agent reasoning and learning. Tabula rasa means the agent learns from scratch through environment interaction, while first principles means decomposing a goal into fundamental truths and using targeted agents to solve them. [1, 2, 3, 4, 5]

But NodeAgent should **not** be tabula rasa at the reasoning layer.

For production, the harness must start from **first principles**:

```text
What is the user trying to produce?
What source artifacts exist?
What facts are manual vs verified?
What cells/blocks could be affected?
What tools are allowed?
What must be evidence-bearing?
What is safe to auto-commit?
What requires review?
```

Your uploaded architecture notes already point toward this: a clean harness separates the AI “brain” from the environment that owns tools, memory, state persistence, lifecycle hooks, approval gates, circuit breakers, and sanitization.  The repo’s target agrees: every user message becomes an intake event, expensive work gets PlanPreview, affected sets include formulas/charts/memos/source refs/human edits/proposals/claims/privacy boundaries, and durable writes must be owned by the harness, not the LLM. 

So the practical answer is:

> **A new room starts blank. NodeAgent does not. NodeAgent starts with skills, schemas, policies, eval contracts, and a first-principles planner.**

# 15. The first-principles execution order

Do **not** try to build all workflows equally.

Use this order:

```text
1. Startup diligence singular company
   because it is the cleanest room demo.

2. Bulk company diligence
   because it shows multi-agent parallelism.

3. Runway / milestone chart
   because it gives the visual wow.

4. C2 vs A1:C5 no-clobber
   because it proves NodeRoom’s differentiated collaboration harness.

5. Finance cost reconciliation
   because it tests evidence-bearing spreadsheet writes.

6. SpreadsheetBench edit-plan
   because it proves benchmark discipline.

7. Private 3-statement collaborate
   because it is highest-value but highest-risk.

8. Visual citation / FinRAGBench-V
   because it requires source-document infra.

9. Finch multi-artifact workflow
   because it is the full long-horizon enterprise case.
```

That order gives you a demo spine first, then benchmark depth.

# 17. Final engineering thesis

The cleanest answer to the user’s whole question is:

> **To accomplish the extracted benchmark workflows on NodeRoom, NodeAgent must become a first-principles harness, not a blank-slate learner: it needs typed intake, PlanPreview, affected-set planning, source-aware world models, evidence-bearing tools, formula-aware patch bundles, managed CAS writes, semantic rebase for stale conflicts, and human-readable review artifacts. The room can start blank; the harness cannot.**

And the interview version:

> **A fresh NodeRoom starts with no data, but it does not start without rules. The agent begins from domain skills, workflow contracts, tool schemas, evidence policies, and concurrency invariants. Then every user request becomes a planned, traceable, reviewable artifact mutation — not just a model response.**
