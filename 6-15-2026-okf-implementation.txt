Cursor added semantic search and measured a 24% increase in answer accuracy on their composer model, a 2.6% gain in code retention in large codebases, and a 2.2% drop in dissatisfied user requests. The Twitter "RAG is dead" discourse and the actual usage curve are moving in opposite directions.

Kuba Rogut's argument is that the problem was never retrieval, it was the narrow definition of it. RAG is not just a vector search call. It is vector search, full text search, glob, regex, and filters used iteratively by an agent that keeps searching until it has what it needs. He contrasts Claude Code (grep per session, no index, repeat cost every run) with Cursor (one time upfront indexing, lightweight tool calls at runtime). Claude Code's approach is not wrong, it is a deliberate tradeoff. The frame that clarifies it: embeddings are cached compute, and whether to cache depends on query volume. Jeff Dean's version: you do not need a trillion tokens at once, you need the right million.

But the architecture point is right: retrieval is cached compute, and strong agent retrieval is not one vector call. It is a search loop.

OKF is a good substrate because Google defines it as a vendor-neutral, human- and agent-friendly format for metadata, context, and curated knowledge, represented as directories of Markdown files with YAML frontmatter. The blog emphasizes that OKF is “just markdown,” “just files,” and “just YAML frontmatter” with queryable fields like type, title, description, resource, tags, and timestamp. The OKF spec says a concept is one Markdown file, the file path is the concept identity, links express relationships, citations support claims, and type is the required frontmatter field consumers use for routing/filtering.

1. Final thesis

Use this as the design sentence:

Convex is the live room ledger. OKF is the portable knowledge bundle. Hybrid retrieval is how NodeAgent finds the right evidence. Managed CAS/proposals are how the agent safely changes shared artifacts.

Or even tighter:

NodeAgent should not remember everything; it should know how to search the right indexed knowledge until it has enough evidence to act.

This fits your existing harness direction: the model is the brain, but the harness owns tools, memory, state persistence, approval gates, rollback, and safety. Convex optimistic UI gives local speed, but durable truth still reconciles through the database.

5. Agent retrieval loop

This is the real “RAG is not dead” implementation.

================================================================================
NODEAGENT ITERATIVE RETRIEVAL LOOP
================================================================================

User asks:
  “Explain CardioNova runway and what source supports it.”

1. Parse intent
   entity = CardioNova
   topic = runway
   output = answer + evidence + review status

2. Check current room surface
   room_current_surface()
   room_recent_context(public, 20)

3. Search OKF
   okf_semantic_search("CardioNova runway burn cash")
   okf_filter(type = "Metric", tags = ["runway"])
   okf_backlinks("companies/cardionova")

4. Search spreadsheet
   sheet_semantic_search("CardioNova runway burn cash")
   sheet_read_range_with_versions(candidate cells)

5. Resolve literal sources
   source_resolve_citation(evidence ids)
   source_open_literal(page/row/cell/bbox)

6. Check sufficiency
   Does evidence support:
     current cash?
     burn?
     funding stage?
     time period?
     formula?
     manual-vs-verified status?

7. If insufficient:
   linkup_search("CardioNova current cash monthly burn funding", "standard")
   or create needs_review coach cue

8. Compose answer
   If enough:
     answer with citations
   If partial:
     answer with caveat and needs_review
   If writing:
     produce CellPayload patch with evidence refs and base versions

The stop condition is not “top 5 chunks returned.” The stop condition is:

type EvidenceSufficiency = {
  enoughToAnswer: boolean;
  enoughToWrite: boolean;
  enoughForClientReady: boolean;
  missing: Array<
    | "source_file"
    | "literal_locator"
    | "period"
    | "definition"
    | "formula"
    | "human_review"
    | "confidence"
  >;
};

For finance/banking:

enoughToAnswer:
  maybe yes, with caveat

enoughToWrite:
  yes, if status = needs_review or estimate

enoughForClientReady:
  only if source, period, definition, formula, and review state all pass

7. OKF chunking strategy

Do not embed only entire files.

type OKFSearchChunk = {
  chunkId: string;
  conceptId: string;
  path: string;
  type: string;
  title: string;
  sectionHeading?: string;
  text: string;
  tags: string[];
  resource?: string;
  targetRefs: string[];
  citationRefs: string[];
  tokenCount: number;
  contentHash: string;
  embeddingModel?: string;
  embedding?: number[];
};

Chunk levels:

L0 Concept card
  frontmatter title + description + tags + resource

L1 Section chunk
  each markdown heading section

L2 Evidence chunk
  claim + citation + support level

L3 Table row chunk
  source coverage tables, metric tables, task tables

L4 Graph neighborhood chunk
  generated summary of links/backlinks around a concept

Example retrieval:

Question:
  “What changed in CardioNova runway?”

Search:
  L0 company card
  L1 runway metric section
  L2 evidence chunk
  L4 backlinks to chart + review cue + trace
8. Hybrid ranking

Use a blended ranker instead of blindly trusting semantic similarity.

finalScore =
  0.35 * semanticScore
+ 0.25 * fullTextScore
+ 0.15 * metadataScore
+ 0.10 * graphProximityScore
+ 0.10 * freshnessScore
+ 0.05 * authorityScore
- privacyPenalty
- stalePenalty
- unsupportedClaimPenalty;

Authority order for NodeRoom:

Uploaded source file / official filing / company source document
  > source artifact extracted from uploaded XLSX/PDF
  > company website
  > credible news / funding article
  > Linkup/web snippet
  > manual chat note
  > generated summary

Manual chat notes are useful, but must stay labeled as manual evidence.

        sufficiency,

    },
  ];
}

Do not embed whole files only. Use concept-level and section-level chunks.

  chunkId: string;
  conceptId: string;

  type: string;
  title: string;
  sectionHeading?: string;
  text: string;

};

Chunk levels:

L0: concept card
  title + description + tags + resource

L1: section chunk
  each markdown heading section

L2: evidence chunk
  claim + citation + support status

L3: table row chunk
  for OKF tables such as source coverage or metrics

L4: backlink neighborhood
  generated summary of linked concepts

8. For artifact writes, produce `CellPayload` with evidence refs.

## Public agent in a room session

The public room agent should use OKF as the **shared room memory and evidence graph**.

### Public agent can read

The public agent should read only:

- `visibility: public`
- room-visible artifacts
- public messages
- public traces
- public evidence
- approved/promoted private outputs
- redacted concepts explicitly marked safe

It should not read:

- private lane messages
- private scratch concepts
- owner-only drafts
- unpromoted private agent reasoning
- hidden source material not visible to the requester

### Public agent retrieval flow

For public agent questions, use this order:

1. `okf_list_concepts`  
   Discover what room knowledge exists.

2. `okf_semantic_search` / `okf_full_text_search`  
   Find relevant evidence, metrics, cells, sources, traces.

3. `okf_read_concept`  
   Open specific concepts before citing them.

4. `okf_backlinks` / `okf_expand_neighbors`  
   Follow relationships:
   - source → cell
   - cell → metric
   - metric → chart
   - chart → coach cue
   - cue → review round

5. `source_resolve_citation` / `source_open_literal`  
   Open original source evidence before making a strong claim.

6. `source_compare_claim`  
   Validate whether the evidence supports, partially supports, contradicts, or fails to support the claim.

7. `read_range`  
   Re-read current cell values and versions before any write.

8. `write_locked_cell_results`  
   Write evidence-bearing outputs through managed lock/CAS.

### Public agent write rule

The public agent should never write loose claims.

It should write:

- evidence-bearing cell payloads
- review proposals
- trace events
- public OKF concepts
- draft handoff artifacts

And it should always use:

- managed lock
- CAS
- proposal/draft fallback
- trace logging

So the public agent's mental model becomes:

> "Search shared OKF, verify source evidence, re-read current room state, then write through managed CAS."

## Private agent in a room session

The private agent should use OKF as a **private overlay on top of the shared room graph**.

### Private agent can read

A private agent for user `U` can read:

1. public room OKF
2. redacted room OKF
3. `visibility: private` concepts where `ownerId = U`
4. private lane messages owned by `U`
5. private scratch drafts owned by `U`

It should not read:

- another user's private OKF
- another user's private messages
- unredacted private source concepts owned by someone else

### Private OKF overlay

Each user should effectively get:

> `effectivePrivateContext = publicRoomOKF + ownerPrivateOKF`

So private agent retrieval becomes:

- search shared public room knowledge
- search private owner-only notes/messages/drafts
- reason privately
- produce private response
- optionally create a private draft concept
- only promote to public if user explicitly chooses room/publish mode

### Private agent write modes

The private agent should have two modes.

#### Mode 1 — Private consult

Default behavior.

Writes only to:

- private channel message
- private OKF concept
- private draft
- private trace if needed

Visibility:

- `private`

Use cases:

- "What should I ask the founder?"
- "Is this company risky?"
- "Draft a banker-facing note, but don't publish it yet."
- "Compare this privately against my thesis."

#### Mode 2 — Promote / act in room

Explicit user action.

The private agent can publish to the shared room only after:

1. user selects "Room" lane or "Promote"
2. private concepts are redacted/converted to public-safe form
3. source evidence is resolved
4. current room state is re-read
5. shared artifact writes go through managed lock/CAS

Visibility transition:

- `private` → `redacted` → `public`

This gives you a clean story:

> "Private agents can think with you. They do not leak into the room unless you promote the result."

---

## The most important privacy boundary

Do **not** use one flat room vector index for everything.

Use partitioned retrieval.

At minimum, every OKF concept/chunk should be scoped by:

- `roomId`
- `visibility`
- `ownerId` when private
- `artifactId`
- `sourceArtifactId`
- `createdBy`
- `createdAt`
- `confidence/status`

The public agent query filter should be:

- `roomId = currentRoom`
- `visibility in ["public", "redacted"]`

The private agent query filter should be:

- `roomId = currentRoom`
- and either:
  - `visibility in ["public", "redacted"]`
  - or `visibility = "private" AND ownerId = currentUser`

That prevents accidental cross-user leakage.

### Repo OKF

1. scan docs + key source files
2. generate OKF concepts
3. link claims to files/snippets/evals

   - engineer receipt doc

   - README claim matrix

Room-level OKF is **live, permissioned, and queryable**.

## Alternatives and trade-offs

### Alternative A — OKF as export only

Use OKF only when exporting a room.

**Pros**
- simpler
- lower privacy risk
- easier to ship

**Cons**
- agents do not benefit from OKF during the session
- no live evidence inspector
- less impressive product story

### Alternative B — OKF as live retrieval layer

Use OKF during the room session.

**Pros**
- better agent context
- stronger evidence model
- enables Trace Lens and review packets
- differentiates NodeRoom from chat apps

**Cons**
- must enforce permissions carefully
- indexing/outbox complexity
- needs evals for retrieval correctness

### Alternative C — best path

Use both:

- **live OKF for active room retrieval**
- **exportable OKF bundle for portability/audit**

That is the strongest architecture.
