# Graph integration: what room events can honestly claim

NodeRoom's live graph rail (`src/ui/graph/LiveGraphRail.tsx`, mounted in
`src/ui/RoomShell.tsx`) feeds the room's real trace log into the vendored
`@homenshum/nodegraph-live` renderer (`vendor/nodegraph-live/`). The renderer
enforces a trust grammar with three edge classes
(`vendor/nodegraph-live/dist/graph-model.d.ts`):

- **evidence** — a MEASURED relationship; the weight came from an external
  system of record and owns the width channel.
- **traversal** — interaction history; "telemetry about us, not evidence about
  the world", constant width, lighter ink.
- **assertion** — a curated claim carrying a complete source receipt, rendered
  with a release badge.

This document answers one question honestly: **which of those classes can a
NodeRoom event actually earn, and what would it take to earn the others?**

The recorded proof at the top of the README
(`docs/release/media/live-graph-rail.gif`, regenerated by
`scripts/record-live-graph-rail.mjs`; the CI-shaped gate is
`scripts/capture-live-graph-rail.mjs`) shows the answer on screen: 13 entities,
14 edges, 34 events — and every one of those edges is traversal.

## (a) The real trace-event taxonomy

`TraceType` is a closed union (`src/engine/types.ts:389`). Every event is a
`TraceEvent` (`src/engine/types.ts:398`): `{ id, roomId, ts, actor, type,
summary, refs?, detail? }` — `summary` and `detail` are prose strings and
`refs` is an untyped `Record<string, string>` of ids. **No field of any trace
event carries a measured number or a versioned source receipt.** That single
fact determines every row of the table below.

Entity extraction is uniform across all event types
(`traceParticipants`, `src/ui/graph/LiveGraphRail.tsx:27`): the **actor**
always becomes a node; the artifact named by `refs.artifactId` becomes an
**artifact** node when its title resolves; `refs.elementId ?? refs.cell`
becomes an **element** node scoped under that title. The `type` never changes
what is extracted — only which refs happen to be present does.

| Event family | Types (emission site in `src/engine/roomEngine.ts`) | Entities extracted | Anything measured? | Trust class earned, and why |
|---|---|---|---|---|
| Edit | `edit_applied` (:324, :617, :633), `edit_blocked` (:412, :604), `semantic_conflict` (:624) | actor + artifact + element | No. The CAS write verifies `baseVersion` (`ChangeOp`), but the version transition is recorded only in prose `summary`/`detail`, never as a typed field | **traversal** — the pair was walked together; nothing external was counted |
| Lock | `lock_acquired` (:368), `lock_released` (:384), `lock_denied` (:357, :378) | actor + artifact + element (first locked element via `refs.cell`) | No. Lock ids and reasons are strings | **traversal** — a lock proves intent and ordering, not a fact about the world |
| Draft | `draft_created` (:730), `draft_merged` / `draft_conflict` (:744) | actor + artifact when `refs` carry one (draft traces carry `draftId` only, so usually actor-only) | No. `smart_merge · N applied, M flagged` exists — but inside the prose `detail` string | **traversal** — and often no edge at all, because a single participant can't make one |
| Proposal | `edit_proposed` (:423), `proposal_resolved` (:701, :708), `proposal_resolve_failed` | actor (+ artifact/element when refs present; `:423` and `:708` carry `proposalId` only) | No. The approved `Proposal` has a review pipeline with a `verified` status (`src/engine/types.ts`, `Proposal.review.status`), but the trace event does not carry the reviewed source | **traversal** — approval is a human decision recorded, not yet a receipted claim |
| Agent status | `agent_session_started` (:810), `agent_status` (:818) | actor only (no artifact refs) | No | none — one participant, zero edges; the node appears, which is honest: the agent exists, it has proven nothing |
| Room/membership | `room_created` (:146), `member_joined` (:161), `auto_allow_toggled` (:170), `schema_changed` (:253), `message` | actor (+ artifact for `schema_changed`) | No | **traversal** at most |
| Work-plan / surfaces | `agent_work_plan_proposed`, `agent_work_plan_approved`, `notebook_read_model`, `nodeslide_authorized`, `nodeslide_receipt` | same uniform extraction; edges only when refs name an artifact | No typed measurement. `nodeslide_receipt` is the closest miss: an event *named* receipt whose receipt lives outside the trace payload | **traversal** |

The dedup rule is the one guarantee the feed adds: the trace `id` is passed as
`eventId` (`src/ui/graph/LiveGraphRail.tsx:67`), and the session remembers the
canonical payload per id (`vendor/nodegraph-live/dist/session.d.ts`: "a reused
explicit id with new content is a conflict, not a duplicate to silently
ignore"), so replaying a trace never strengthens an edge.

## (b) What the wiring feeds, and what it refuses

The renderer's `GraphSession.observe` contract
(`vendor/nodegraph-live/dist/session.d.ts`):

> Exactly two participants plus a measured conjunction produce evidence. Three
> or more participants, or a pair with no measurement, produce only traversal
> telemetry. A measured zero still produces evidence weight 0.

`LiveGraphRail.tsx` deliberately never supplies the measurement. The feed line
(`src/ui/graph/LiveGraphRail.tsx:66-67`):

```ts
// measuredCount stays undefined: room events measure nothing.
if (entities.length > 0) session.observe(entities, undefined, { eventId: t.id });
```

and the header contract (`src/ui/graph/LiveGraphRail.tsx:8-13`):

```
 *   - Room events carry NO measured registry counts — measuredCount is always
 *     undefined, so entities read "unknown — not measured" and every edge is
 *     interaction history (traversal), never measured evidence.
 *   - assertEdge is NEVER called: the keyless demo path has no versioned
 *     curated source to receipt, so no curated assertion edges exist here.
```

The refusal is also stated on the surface itself, not just in comments — the
rail's footer caption (`src/ui/graph/LiveGraphRail.tsx:130-132`):

```
Built from real room events (trace log). Edges are interaction history; room events carry no
measured counts, so entities read "unknown — not measured". No curated assertion edges: the
keyless demo path has no versioned source to receipt.
```

So the wiring **feeds**: real actors, artifacts, and elements from every trace
event, deduplicated by trace id, into a bounded FIFO-evicted session. It
**refuses**: measured weights (`measuredCount` hard-coded `undefined`),
curated assertions (`assertEdge` has zero call sites in `src/`), and any
LLM-invented entities (extraction is a pure function of `TraceEvent` fields —
no model is consulted; see `traceParticipants`,
`src/ui/graph/LiveGraphRail.tsx:27-37`).

## (c) The named API gaps

Two typed gaps stand between "everything is traversal" and an earned upgrade.
Both are field-level, not architectural.

**Gap 1 — no measured field on `TraceEvent`, so evidence is unreachable.**
`GraphSession.observe(entities, measuredCount?)` will mint an evidence edge
for exactly two participants plus a number
(`vendor/nodegraph-live/dist/session.d.ts`). The room can never pass that
number because `TraceEvent.refs` is `Record<string, string>` and every numeric
outcome the engine actually verifies — the CAS `baseVersion → version`
transition on an applied edit, `applied.length` from a smart-merge
(`src/engine/roomEngine.ts:745`) — is flattened into the prose `detail`
string. The fix is a typed optional field, e.g.
`measured?: { value: number; source: string; asOf: number }` on `TraceEvent`
(`src/engine/types.ts:398`), populated **only** where a number was verified
against a system of record. The honesty caveat is real, and it is why the
current wiring refuses rather than plumbing the easy numbers through: op
counts and version bumps are measurements *of our own activity* — the
renderer's own model doc classifies that as "telemetry about us, not evidence
about the world" (`vendor/nodegraph-live/dist/graph-model.d.ts`). The event
that would legitimately earn evidence is one whose number came from outside
the room: e.g. a research-sheet import (`add_research_rows`,
`src/engine/roomEngine.ts:324`) whose row value is a count fetched from a
registry, carried as `measured: { value, source: "<registry>", asOf }`.

**Gap 2 — refs carry no release, so assertion is unreachable.**
`assertEdge` demands a complete `AssertionReceipt`
(`vendor/nodegraph-live/dist/graph-model.d.ts`):

```ts
export type AssertionReceipt = {
    source: string;      // curating system of record
    release: string;     // versioned release containing the assertion
    subjectId: string;   // stable source identifiers for both endpoints
    objectId: string;
    url: string;         // literal HTTP(S) URL that re-opens the assertion
};
```

NodeRoom is closer to this than it looks. The semantic graph layer already
classifies cells as `source_backed` (`SemanticGraphStatus`,
`src/ui/graph/semanticGraphTypes.ts:40`) and its ref type already carries
`sourceUrl`, `traceId`, and `proposalId`
(`SemanticGraphRef`, `src/ui/graph/semanticGraphTypes.ts:51-67`). What it
lacks is exactly what the receipt demands and the ref type omits: a
**release/version stamp** and **stable subject/object ids**. This is the same
gap NodeGraph's own compose example names as its deliberate refusal
(`NodeGraph/README.md`, `examples/compose`): "the model's relevance weight is
not a measured count and its refs carry no release, so every relationship
renders as traversal — the refusal is the demo"; its product audit lists the
fix as item 1 ("the renderer's `assertion` class needs the model to grow an
optional release-stamped ref",
`NodeGraph/docs/PRODUCT_AUDIT_2026-08-12.md`). The concrete change: add
optional `release?: string` and `sourceId?: string` to `SemanticGraphRef`,
stamp them at capture time (the Firecrawl ingestion path knows the fetch URL
and time), and have proposal approval carry the ref into the trace — a
`proposal_resolved` event for an **approved** proposal whose op targets a
`source_backed` cell with a release-stamped ref is a curated, source-backed,
human-approved claim, which is precisely what `assertEdge` exists to render.
The approval flow even has the reviewer slot already:
`Proposal.review.status: "verified"` (`src/engine/types.ts`).

A third, smaller gap: `TraceEvent.refs` being untyped means the rail
discovers `elementId ?? cell` by convention
(`src/ui/graph/LiveGraphRail.tsx:33`); typing refs per `TraceType` would make
the extraction contract checkable instead of conventional.

## (d) The next honest upgrade

The next upgrade should be the assertion path, not the evidence path, because
the room already contains every ingredient except one field: it has
source-backed cells with literal source URLs
(`src/ui/graph/semanticGraphTypes.ts`), a human approval act that is exactly
what "curated" means (`approveProposal`, trace at
`src/engine/roomEngine.ts:708`), and a review pipeline that can mark the
claim `verified` (`src/engine/types.ts`). Adding `release` + `sourceId` to
`SemanticGraphRef`, stamping them at ingestion, and calling
`session.assertEdge(actor, cell, receipt)` from the rail **only** on
approved proposals over source-backed refs would put the first badge-bearing
assertion edges on the graph with a complete replay receipt behind each one —
while edits, locks, drafts, and agent status stay traversal, and evidence
stays refused until a room event carries a number measured outside the room.
That ordering keeps the property that makes the rail worth trusting: an edge
class is never a style choice, it is a statement about where the weight came
from, and today every honest answer to that question is "we walked there
together."
