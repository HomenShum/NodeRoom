I pulled the latest main files and reviewed the new NodeRoom direction around passive room intelligence, Firecrawl/source capture, OKF retrieval, entity caching, and durable agent work items. I did not run the repo locally, so this is a GitHub/code review, not a verified green-test report.

What changed

The biggest change is that NodeRoom is no longer just “user explicitly asks agent → agent runs.” It now has the beginnings of a passive intelligence loop:

user types in note / spreadsheet / wiki / message
  -> Convex saves the committed content
  -> server-side debounce waits for quiet time
  -> scanner decides if the content is noteworthy
  -> if meaningful, creates agentJob + entityWorkItems
  -> later workflow can research/cache/fill/source/OKF-index it

The new roomActivityOutbox schema tracks saved content events, quiet windows, scheduled scans, dedupe keys, findings, and the latest linked agent job. That is the backend foundation for “user typed something, put the phone away, and NodeRoom noticed it was worth following up.”

The new convex/noteworthy.ts implements a keyed server-side debounce. When a node/cell/wiki/message is saved, debounceActivityScan cancels the prior scheduled scan for that same object and schedules a new scan after the quiet window. This prevents agent work on every keystroke.

When the quiet-window scan fires, scanActivity re-reads the latest committed content, runs a cheap noteworthiness classifier, and, if the content is meaningful, creates a durable agentJob plus entityWorkItems. The current implementation is a P0 scaffold: it creates the work ledger, but the expensive downstream research workflow still needs to process those work items.

The repo also added an Evidence Accountant layer. sourceCaptures stores captured source URL/title/kind, content hash, Markdown/HTML/screenshot storage IDs, provider, visibility, and owning job; evidenceFacts stores extracted facts, values, units, period, quote, selector/bbox, confidence, checks, and downstream usage. This matches the earlier design: screenshots alone are not enough; banker-grade evidence needs raw source, screenshot, text, bbox, extracted fact, verifier receipt, and downstream artifact links.

The OKF layer is now real in schema: okfConcepts, okfChunks, okfEdges, and okfOutbox support portable room knowledge, full-text search, vector search, links/citations/backlinks, and reindexing jobs. entityResearchCache stores entity/facet-level cached results with source-set hashes, result hashes, freshness windows, and delta status — exactly what we need to avoid duplicate Linkup/Firecrawl/LLM calls.

Finally, ConvexRoomTools now wires OKF retrieval into the agent harness. The same RoomTools contract works over memory mode or Convex; in production, it maps OKF list/read/search/filter/glob/regex/backlinks/open-literal/compare-claim operations through Convex queries and records retrieval events.

Why these changes were made

The product reason is simple:

The core happy path is relationship capture → source-backed diligence fill.

A banker, analyst, founder, or conference attendee may not always click “run agent.” They may just type:

Met Maya from CardioNova. AI triage for hospitals. Possible Series B. Ask about burn and pilots.

or they may add a row in the spreadsheet and walk away.

Before these changes, NodeRoom depended more heavily on explicit prompts. After these changes, the room can begin to behave like a background analyst assistant:

notice useful note
identify company/person/topic/funding/runway/task signals
reuse cached research if fresh
create entity work only if missing/stale
capture evidence
backlink the note
fill or propose spreadsheet updates

The infrastructure also supports lower cost. Entity/facet caching lets the room avoid repeating paid search, scraping, embedding, and LLM synthesis when a company/product/person has already been researched and the source set is still fresh.

Trade-offs and alternatives

The main trade-off is complexity. We now have more moving pieces:

roomActivityOutbox
noteworthy scanner
agentJobs
entityWorkItems
entityResearchCache
sourceCaptures
evidenceFacts
okfConcepts
okfChunks
okfEdges
okfOutbox
retrievalEvents

That is more to test and maintain. The upside is that the architecture now matches the actual product vision: passive capture, background research, source-backed output, and reusable room memory.

A simpler alternative is a pure manual model:

user writes note
user clicks “Research”
agent runs only then

That is easier, cheaper, and safer. The downside is weaker magic and weaker “phone-away” utility.

Another alternative is to use a full external workflow engine or queue system. But since NodeRoom already uses Convex for live state, the current design keeps workflow intent, activity, source evidence, and room state in one operational ledger. The broader harness idea remains: the LLM is not the system of record; the harness owns tools, state, approval, rollback, and safety.

The biggest technical caution: the new passive scanner should stay cheap. It should not call Linkup, Firecrawl, or an LLM directly during every scan. It should classify cheaply, create durable work, and let a workflow/workpool process expensive research under budget/caching rules.

How Convex mutations, actions, and queries fit together

The operational flow should be visualized like this:

1. User commits content
   - notebook node edit
   - spreadsheet cell edit
   - wiki revision
   - chat message

2. Convex mutation saves the content
   - updates node/element/message/wiki row
   - bumps version/hash
   - calls or is followed by debounceActivityScan

3. debounceActivityScan mutation
   - authenticates user
   - cancels previous scheduled scan for this source
   - schedules scanActivity after quiet window
   - writes/updates roomActivityOutbox

4. scanActivity internal mutation
   - re-reads latest saved content
   - skips if superseded
   - classifies noteworthiness
   - creates agentJob + entityWorkItems if useful

5. later action/workflow
   - checks entityResearchCache
   - searches OKF concepts/chunks/edges
   - calls Linkup/Firecrawl/LLM only if missing or stale
   - creates sourceCaptures/evidenceFacts

6. managed mutation
   - writes CellPayloads
   - creates proposals if risky
   - updates OKF concepts/outbox
   - records traces/retrieval events

Queries serve the UI and agent retrieval. For example, OKF exposes full-text search, semantic search, filters, glob, regex, backlinks, neighbor expansion, citation resolution, literal source opening, and claim comparison. In the Convex adapter, the agent uses these through ConvexOkfRetrievalPort, and semantic search first tries Convex vector search before falling back to a scan path for local/test environments.

This is the key idea:

Mutations commit truth. Actions/workflows do slow external work. Queries retrieve current state and knowledge. The agent never gets to directly bypass managed writes.

2. Separate the two debounces: save debounce vs. agent debounce

These are different systems and should never be conflated.

Typing debounce:
  protects UX and database write volume.

Agent debounce:
  protects model/search/API cost and avoids noisy automation.
Layer A — save debounce

This is short.

Goal:
  keep the user’s text saved and shared.

Typical timing:
  300–1000ms after typing pause
  immediate on blur
  immediate on pagehide / phone lock
  immediate on manual save

This mutation should only save content. It should not call an LLM or Firecrawl.

Layer B — passive agent debounce

This is longer.

Goal:
  wait until the note/cell is stable enough to inspect.

Typical timing:
  8–20 seconds after quiet period
  maxWait 30–90 seconds from first meaningful edit
  batch window for busy rooms

The current implementation is already moving in the right direction. debounceActivityScan persists the latest source hash/version, cancels a prior scheduled scan for the same source, and schedules scanActivity after the quiet window. Convex scheduled functions are stored durably and can be canceled before they run, which is exactly the right primitive for server-side debouncing.

3. Fix the “shared notebook never kicks off” problem

Your edge case is real:

Public notebook constantly updated by User A, User B, User C.
If debounce key = notebookId,
the quiet window may never arrive.

The fix is: never debounce at whole-notebook granularity.

Use scoped debounce keys.

Good debounce keys
Notebook block:
  roomId + nodeId + authorId + editingSessionId

Spreadsheet cell:
  roomId + artifactId + elementId + authorId

Spreadsheet row note:
  roomId + artifactId + rowId + columnGroup + authorId

Message:
  roomId + messageId

Wiki paragraph:
  roomId + wikiPageId + blockId + authorId

So if three users type in the same public notebook, each user/block gets its own quiet window.

Add maxWait

Even per-user debouncing can be delayed if one user keeps typing forever. Add a maxWait:

quietUntil = lastEditAt + 12_000;
forceScanAt = firstEditAt + 60_000;

scan when:
  now >= quietUntil OR now >= forceScanAt

That gives you:

Trailing debounce:
  wait for the user to pause.

Max wait:
  eventually scan a snapshot even if the user keeps typing.
Does per-user debouncing create too many Convex operations?

It can, if you call it on every keystroke.

The rule should be:

Client keystrokes:
  local only

Client save:
  debounced content mutation

Server agent debounce:
  one scheduled function per source key, cancel/reschedule

So the operation count is approximately:

not keystrokes × users
but saved blocks/cells × active editing sessions

The current schema already supports this: roomActivityOutbox stores source kind/id/version/hash, event kind, status, actor, visibility, dedupe key, quiet window, scheduled function id, attempts, finding, and latest job id.

5. Layer two: agent jobs should not disrupt other users

The agent should not blast every user with every update.

Use four output levels:

Level 0: private scratch
  Only agent/harness sees it.

Level 1: quiet room status
  “Researching CardioNova…”

Level 2: proposal / insight card
  Reviewable by humans.

Level 3: durable artifact update
  Batched CellPayload / note / chart changes.

For text, use persistent text streaming for narration, not spreadsheet truth. The Convex persistent text streaming component streams text over HTTP to the active client while persisting it in the database; its example notes that the live HTTP stream can send tokens immediately while the database updates at sentence boundaries for other subscribers.

So:

Owner/private user:
  can see token-level stream.

Other room users:
  see sentence-level chunks or job summary.

Spreadsheet:
  receives final/batched evidence-backed patches only.

This aligns with the Convex optimistic UI model we discussed: optimistic updates are local temporary cache overlays; authoritative state still comes from the server after mutation reconciliation.

6. Avoid bandwidth blowups from agent-populated results

Do not let agents write one cell at a time if the job produces many outputs.

Bad:

50 facts found
  -> 50 mutations
  -> 50 query invalidations
  -> 50 UI flashes
  -> 50 websocket updates per subscribed client

Good:

50 facts found
  -> one patch bundle
  -> compare payload hashes
  -> skip unchanged cells
  -> one managed batch write
  -> one UI diff

For NodeRoom, the agent output path should be:

Agent workflow
  -> EvidenceMemo[]
  -> CellPayload[]
  -> payloadHash comparison
  -> write_locked_cell_results batch
  -> OKF concept update
  -> one status event

Only users viewing that specific artifact/range should receive the cell patch. Users elsewhere see a small Signal Tape update:

“CardioNova enriched · 7 fields · 2 review”

Figma is a useful reference for graceful multiplayer degradation. Its help docs state that Figma has multiplayer limits and adjusts the experience for performance: up to 200 cursors shown, 200 editors, and 500 total participants before view-only/static behavior changes. NodeRoom should copy the principle:

In small rooms:
  rich presence and live updates.

In large rooms:
  fewer cursors, fewer live details, more summaries, view-only/deferred updates.

13. Concrete implementation plan
P0 — fix first-use and debounce starvation
1. Open Capture Notebook by default.
2. Add placeholder guide text and three quick actions.
3. Debounce save per block/cell, not whole notebook.
4. Debounce agent scan per actor/source/session.
5. Add maxWait so long typing still creates a snapshot scan.
6. Add Noteworthy Inbox for “suggest first” behavior.
P1 — reduce disruption and bandwidth
1. Agent writes to scratch/proposals first.
2. Batch CellPayload writes.
3. Skip unchanged payload hashes.
4. Stream text only through persistent text streaming.
5. Observers get sentence chunks or summaries, not token-level updates.
6. Only subscribed artifact/range users receive detailed patch updates.
P2 — batch high-volume rooms
1. Add batchScanRoomActivity(roomId).
2. Group by entity/facet/privacy.
3. Use one parent agentJob per window.
4. Use entityWorkItems for child work.
5. Add single-flight active job dedupe.
6. Use room/workspace/global public cache.
P3 — stress test
1. Build synthetic room load generator.
2. Run notebook starvation scenario.
3. Run conference repeated-topic scenario.
4. Run persistent text streaming observer load.
5. Run 200-cell batch patch scenario.
6. Record cost, latency, bandwidth, render counts, and dedupe rates.

The final rule:

Type fast, save quietly, scan patiently, research in batches, stream summaries, and mutate shared artifacts only with evidence-backed batches.
